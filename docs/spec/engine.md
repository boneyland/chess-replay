# Engine

[Spec](../spec.md) › what is built. The browser's Stockfish beyond the basics in [Replay](replay.md): the full engine download, lines (MultiPV), threads and the asm.js fallback.

## Full Stockfish download

Some viewers want the strongest engine, as Lichess offers for local analysis. The Analysis panel's engine drop-down: **Stockfish 19 lite** (the default) or **Stockfish 19 full** (99 MB, said by its Download button).

- Full is stockfish.js v19.0.1 **`stockfish-19-single`** (28 KB `.js` + 99 MB `.wasm`, the big NNUE net inside), single-threaded here; where the page is cross-origin isolated the multi-thread `stockfish-19` pair is used instead (see Multi-threaded Stockfish). Not committed to git (just under GitHub's 100 MB limit); fetched from `https://unpkg.com/stockfish@19.0.1/bin/` (CORS open), both files checked in the browser against SHA-256s pinned in `app/sf-full.js` (`SFFull`).
- Picking Full before it is downloaded opens the Analysis panel's engine menu (☰), which shows the size (behind the button's ⓘ), where it comes from and a **Download full Stockfish · 99 MB** button; nothing downloads before the click. Progress shows by the megabyte with Cancel. A connection that sends nothing for 30 s (before the answer or between chunks) is given up with "unpkg.com stopped sending …", so a stall can't hang the download; Download tries again. A failed or cancelled download starts again from 0 MB: no resume (see the decisions log, 2026-10-27). Before fetching, `navigator.storage.estimate()` must leave room for the files plus 10%. Nothing is kept unless both files arrive whole (no more, no less than the pinned size) and match.
- The files are kept in the cache `stockfish-full-19`, which `sw.js` never deletes (it clears only `chess-replay-*` caches on a deploy), and the page calls `navigator.storage.persist()` (Chrome decides by itself, Firefox asks). So it is a one-time download, offline afterwards, unless the browser evicts it, the viewer clears site data, or (Safari) the site goes unvisited for 7 days outside a home-screen app.
- Until the copy is kept, and whenever it goes missing, Lite runs. Starting Full trusts the copy checked at download: once per page it compares only the sizes (a missing or cut-short copy is deleted and the setting offers the download again with a note), never reading the 99 MB into the page or hashing it again, and starts the worker from the cache's Blobs as Blob URLs, the glue reading its wasm URL from the `#hash`.
- Switching engines quits the running engine (its searches answer null) and stops a running analysis. The engine wanted is known while rendering, so a panel searching again after the switch gets the new engine, never the one being quit; its partial run keeps its key, which includes the engine name, so it resumes only with the engine that made it.
- The engine name follows the engine that runs: "Stockfish 19 (browser)" for Full (`AnalysisCore.ENGINE_NAMES`, `engineSettings(t, kind)`), and the analysis JSON records it. The own-move eval cache (Go deeper on a stored move too) and the pace estimate (`chess-video.sf-pace.v1.full`) are kept per engine. Play vs Stockfish plays with whichever engine runs.
- A kept copy shows **Remove the full engine download · 99 MB** (with Lite selected too), which asks first: "Remove the full engine? You'd need to download 99 MB again to use it." with **Remove** and **Keep**. A removal the browser refuses says "The full engine could not be removed: …" with its reason, and the setting follows what is still kept (`SFFull.removeKept`), with the question closed, as the board reader's Remove does.
- Tests: `tests/sf-full.test.cjs` (fake unpkg, Cache Storage and Worker: checksum, size, quota, a stalled connection, cancel, a kept copy trusted, a partial copy dropped, remove); the live suite downloads the real files from unpkg in each browser (one retry if the download fails, as unpkg is a third party: a CI run once had Chrome's download not finish in 240 s) while a move rated by Lite is shown, sees Full rate it again without another move, reloads without fetching again and removes the copy.

## Lines (MultiPV)

Analysis › ☰ › **Lines**, 1 to 5 (`sfLines`, default 1), for the searches of the viewer's own moves (the replay's own line and the free board) and for Go deeper on a loaded analysis's moves (renamed from "Your moves: lines" 2026-11-08).

- `SFEngine.search({ lines })` sends `setoption name MultiPV value N` between searches, only when it changes; every other search (the position before the viewer's move, which only rates it, so it goes as deep as one line can; a game's analysis (unless its own Lines setting, below, asks for more); the Stockfish opponent and its "before" search; Go deeper on a stored move, before the Lines setting reached it) asks for 1, so the analysis JSON is unchanged (`lines: 1`). Results gain `lines: [{ k, cp, depth, pv }]`, by rank; `cp`, `pv` and `best` stay line 1's. Line 1 is the search's result; each other line is the move last reported at its rank (a bound-only report included) with that move's last complete score, at whatever depth. With several threads Stockfish ends on the deepest thread's line 1, which can be two depths past the other lines' last complete scores, and the last depth can end mid-way, leaving stale scores by rank: line 2's last report a bound while line 1 has turned to line 2's move, or line 1's last report a bound on a new move while line 2 names line 1's old one. A move already listed is left out, the others renumbered, and a rank left empty takes a move another rank last named (line 1's new move), else the deepest other move with a complete score (a rank's last report can be a bound on a move never scored complete), so a 2-line search lists 2 different moves wherever the engine scored 2.
- With more than one line the Analysis panel lists them, one row each (eval, its first moves in SAN, wrapping under each other beside the eval column); a move plays the line on the board up to it, as Stockfish's replies did. The board shows an arrow per line's first move: line 1 as the best-move arrow, the others thinner and fainter (Settings › Best-move arrows turns them off). One line looks as before.
- The own-move eval cache keys a search of several lines apart from one of one line. A note in Settings says each line gets a share of the search, so goes less deep in the same time.
- On the phone a line's moves take two rows, and the Analysis panel scrolls to the later lines (a row cut off at the panel's edge hid moves there).
- Tests: fake worker (option sent once per change and before the position, lines by rank, a lagging line dropped, White's point of view), settings range, real Stockfish giving 3 different first moves at the start, live: Lines 3 on the free board shows three rows and three arrows.

## Engine lines in analysis files

Built 2026-11-08 (branch `claude/engine-lines`).

- **The format is chess-animator's** (`chess_game_analyzer.py`, its commit 89c41d3 of 2026-11-04). Each move gets `engine_lines`: every line Stockfish returned from the position *before* the move, best first, unfiltered, each `{ move, eval, depth, line }` (`move` the first move in SAN, `eval` in centipawns from White's side, mates as ±(10000 − 10·N), `depth` that line's, `line` its SAN moves from `move` on, up to 12 plies). Beside it: `search_lines` (how many lines returned), `alternative_moves` (`[[SAN, cp]]`: the lines after the first, not the move played, within 50 cp of the best), `best_line` (line 1). The position after the last move has `pv_line` alone.
- **Written** by `AnalysisCore.runAnalysis` (`engineLines`, `alternativesOf`) with as many lines as the game analysis's own **Lines** setting (Analyse the game dialog, `sfGameLines`, 1 to 5, default 1: 3 lines took about 4.5 times as long as 1 at a set depth in chess-animator and weaken multi-threaded search, so the dialog's note says so and the time estimate multiplies by lines^1.37 at a set depth). **Read** by `ChessCore.buildGame`: `ply.nextLines` (the lines of the position after the move: the next move's `engine_lines`, as `{ k, cp, depth, pv: uci }`, only with more than one) and `ply.best.more` (the other lines from the position before a move not rated best, SAN, none starting with the move played). A file without `engine_lines` reads as before.
- **Analysis panel**: on a loaded analysis's move with several lines, the Best line row is replaced by the Lines list (as a search of the viewer's own moves shows them; line 1 is the Best line), with an arrow each on the board while paused. Go deeper's lines (the Lines setting) replace the analysis's for that position.
- **Annotated PGN**: where the engine's line is written (a move not rated best), lines 2 and up follow it as further variations by rank, without evals; none on a move rated best (kept short). Go deeper's lines replace the analysis's (`ChessCore.withSearches`).
- **Not done**: a PGN's own variations beyond the first still show only in the export (the panel lists the first only); chess-animator's video and report don't use `engine_lines` yet.
- Tests: `tests/fixtures/lines_analysis.json` (from `chess_game_analyzer.py` with 3 lines) read by `buildGame`; `runAnalysis` with fake and real engines; `tests/check_browser_json.py` loads a browser file with 3 lines and checks `engine_lines` has the analyzer's shape.

## Multi-threaded Stockfish

Built 2026-10-28 (PR 81, with follow-up fixes). Stockfish searches with several threads where the page is cross-origin isolated; otherwise as before, one thread.

- **Isolation**: `render.yaml` sends `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on `/*` (rollback: delete the two lines). The service worker passes a navigation redirect through so the isolated copy survives offline. No other site may frame the page (below).
- **Files**: lite `stockfish-19-lite.js` + `.wasm` vendored beside the single-thread pair (`stockfish-19-lite-single.*`, the fallback), pinned in LAYOUT.md; full `stockfish-19.js` + `.wasm` from unpkg, pinned in `app/sf-full.js`, kept in the same cache as the single-thread pair (a build replaces the other; a viewer who had the single-thread Full downloads once more).
- **Feature test** (`SFEngine.threadSupport`, as Lichess's `sharedMemoryTest`): `crossOriginIsolated`, `Atomics`, `SharedArrayBuffer`, a shared `WebAssembly.Memory`; off for Safari 26.2.
- **Threads setting** (Analysis › ☰ for the live searches, `sfThreads`; the Analyse the game dialog for the game analysis, `sfGameThreads`; `null` = default): 1 to `min(cores − 1, 8)`, default half the cores, at most 4. Hash table is split the same way (`sfHash`, `sfGameHash`). A viewer who had stored Threads or Hash table before the split gets them for the game analysis too, once (`useTweaks`' `carry`), so a stopped run keyed by them still resumes. `SFEngine` sends `setoption name Threads` only on change, between searches, and per search to threaded builds only. The analysis JSON records the threads the run started with (1 when the engine fell back); `sfPartialKey` and the pace estimate include them.
- **Fallback**: a threaded engine gets up to three starts (Firefox can hang before `uci`, while starting threads, or on its first search); `ready()` also waits for a depth-1 probe search. If it never starts or dies, the page falls back silently to single-thread (Full without a kept single-thread copy runs Lite), Threads is disabled for the rest of the page and the menu says why. A threaded search still running 5 s past its movetime moves to a fresh worker (up to three in a row, then the engine fails).
- **Not done / open**: **verify** on an iPhone whether 64 MB of hash starts or iOS needs Lichess's 32 MB cap; manual checks on the phone (Firefox Beta on Android) and iPhone Safari.

## asm.js Stockfish (no WebAssembly SIMD)

Built 2026-10-31 (PR 120). Every wasm build of Stockfish 19, Lite and Full, single and threaded, uses WebAssembly SIMD, which Firefox on 32-bit ARM Android lacks: on the user's Samsung SM-T510 tablet (Firefox) no engine ever answered, so Go deeper's + just vanished and own moves showed "Stockfish stopped". There the page runs stockfish.js v19.0.1's **`stockfish-19-asm.js`** instead: Stockfish 19 compiled to JavaScript (3.2 MB, vendored, SHA-256 pinned in LAYOUT.md; the same file on npm and the GitHub release), which runs anywhere, its author says "very slow and weak".

- **Test**: `SFEngine.simdSupport()`, `WebAssembly.validate` on a function returning a v128 (wasm-feature-detect's test). Without SIMD the engine kind is `asm` (`sfKind` in `game-app.jsx`, `SF_SIMD` in `stockfish.jsx`): one thread (threads off from the start, so no threaded tries), no Full (`SF_FULL_OFFERED` false), the page's check for the file looks for the `.js`.
- **Name**: "Stockfish 19 asm.js (browser)" (`AnalysisCore.ENGINE_NAMES.asm`), so its own-move results, partial runs, analyses and pace estimate (`chess-video.sf-pace.v1.asm`) stay apart from Lite's and Full's. Until a run has timed enough positions its estimate starts at 8 times Lite's model, as measured (`AnalysisCore.paceStart`; Full starts at 1.3 times), and a measured factor is kept within 0.25–4 times that start.
- **Told**, in red: the engine menu ("This browser can't run Stockfish's WebAssembly (it has no WebAssembly SIMD), so Stockfish runs as JavaScript (asm.js), which is very slow and weak. Open this page in Chrome for full-strength Stockfish."), the line under the Analysis panel in place of the drag-a-piece tip ("No WebAssembly SIMD: Stockfish is very slow and weak here. Use Chrome"), and beside "Analyse with Stockfish". On iPhone and iPad, where every browser is WebKit, both say "Update to iOS 16.4 or later" instead (Safari has SIMD from 16.4).
- **Tests**: `simdSupport` and the asm.js engine answering a search in Node (`tests/sf-engine.test.cjs`), the file pinned and copied (`tests/build.test.cjs`); live (Chromium, Firefox), with the page's `WebAssembly.validate` faked to deny SIMD: only the asm.js file loads, Go deeper reaches a depth and the + comes back, the menu says it's very slow and weak. Measured there: a Go deeper from the sample's move took about 7 s on this laptop.
