# Multi-threaded Stockfish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stockfish (lite and full) searches with several threads when the page is cross-origin isolated, set by a Threads setting, falling back silently to one thread where it can't.

**Architecture:** Render sends COOP/COEP, so the page gets `SharedArrayBuffer`. `SFEngine.threadSupport()` decides whether the threaded builds may run; `useEngine` starts the threaded worker (lite from `vendor/`, full from the kept unpkg download) and on any start failure retries single-threaded. `SFEngine` sends `setoption name Threads` between searches like Hash; `AnalysisCore.engineSettings` carries `threads` into every search, the analysis JSON, the partial-run key and the pace key.

**Tech Stack:** stockfish.js v19.0.1 (`stockfish-19-lite` and `stockfish-19`, Emscripten pthreads), React 18 UMD, Node test runner, Playwright live tests.

**Spec:** `docs/spec.md` › Roadmap › Lichess data and multi-threaded Stockfish › PR 5.

## Global Constraints

- Branch `claude/threads`, small commits, PR against `main` (push and open the PR only when asked).
- Files, pinned exactly: `stockfish-19-lite.js` 33,426 B, `stockfish-19-lite.wasm` 1,697,617 B (vendored); `stockfish-19.js` 33,326 B, `stockfish-19.wasm` 99,076,105 B (unpkg `https://unpkg.com/stockfish@19.0.1/bin/`). SHA-256s computed from the downloaded files and written to `LAYOUT.md` (and `app/sf-full.js` for the full pair).
- Headers on `/*`: `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp`.
- Threads range 1 to `min(hardwareConcurrency − 1, 8)` (at least 1); default `min(4, floor(hardwareConcurrency / 2))`, at least 1; `TWEAK_DEFAULTS.sfThreads = null` means the default.
- One Threads value for every search: game analysis, own moves, Go deeper, the Stockfish opponent and its critique.
- Single-thread builds stay as the fallback; a fallback is silent except the reason under Threads in Analysis › ☰.
- Feature test as Lichess's: `crossOriginIsolated`, `Atomics`, `SharedArrayBuffer`, a shared `WebAssembly.Memory({ shared: true, initial: 1, maximum: 2 })` whose buffer is a `SharedArrayBuffer`; off for Safari 26.2 (user agent contains `version/26.2`).
- Memory rule (CLAUDE.md): the full engine's live test runs alone, never in parallel with another browser; no full-engine Node test.
- Split long lines only in code being changed.

## Review Focus

1. A viewer who downloaded single-thread Full before this ships, on an isolated page: Full shows as not downloaded (the threaded pair), downloads 99 MB once more, and Lite runs meanwhile; never a broken engine.
2. The threaded engine fails to start (nested workers blocked, iOS memory): the page falls back to single-thread within the ready timeout, Threads shows disabled with "The threaded engine didn't start", and analysis works.
3. A stopped analysis resumed after Threads changed starts over (the partial key includes threads); one resumed with the same Threads continues.
4. Changing Threads mid-search: the running search keeps its threads, the next one uses the new count (no worker restart, no lost search).
5. Offline reload of an isolated page from the service worker's copy is still isolated (`crossOriginIsolated` true), so threads keep working offline.
