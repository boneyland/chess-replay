# Chess960 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read, replay, explore and play Chess960 games and positions, with castling by the 960 rules and never by accident.

**Architecture:** A 960 position is a ChessCore position carrying `rooks` (each castling right's rook square); standard positions never carry it, so their code paths stay as today. Inside the page a 960 castle is written king-takes-rook in UCI (`e1h1`, `b1a1`), which is also what Stockfish writes with `UCI_Chess960` on, so engine lines need no conversion. The 960 *label* (PGN `Variant` tag, Game info's "Chess960 #n") is a separate `chess960` field on the board/game.

**Tech Stack:** plain JS IIFE modules on `window` (`app/*.js`), React JSX views (`app/*.jsx`), `node --test` unit tests (`tests/*.test.cjs`, `loadUnit`), Playwright live tests (`tests/live/site.test.cjs`).

**Spec:** `docs/plans/2026-11-13-chess960-design.md` (read it first).

## Global Constraints

- Branch `claude/chess960`, small commits, PR against `main`; no `claude.ai/code` URL in the PR.
- Standard games must look and play exactly as today: every existing test passes unchanged.
- Position 518 plays as standard chess (no `rooks`); only its PGN tag and Game info say Chess960.
- Never an accidental castle in a 960 position: a single drag/click castles only through the confirmation or a Castle button.
- Castles are written `O-O` (h-side) and `O-O-O` (a-side). FENs are written X-FEN (`KQkq` for the outermost rook on that side, the rook's file letter otherwise).
- UI text follows the `ui-text` skill; screenshots desktop 1440×900 and phone 390×844 in Chromium and Firefox, in the PR via the `pr-screenshots` skill.
- Run `node --test --test-concurrency=1 tests/*.test.cjs` before each commit; it must pass.

### Task 1: ChessCore 960 positions and castling

**Files:**

- Test: `tests/chess-core.test.cjs`

**Interfaces (Produces):**
- `ChessCore.chess960Fen(n: 0..959) -> string` six-field FEN, X-FEN rights `KQkq`, Scharnagl numbering.
- `ChessCore.chess960Random(rand = Math.random) -> number` uniform over 0..959 except 518.
- `ChessCore.chess960Number(fen) -> number | null` the number whose start this FEN's placement is (both back ranks mirrored, pawns on 2/7, nothing else), else null.
- `ChessCore.castleRook(b, r: 'K'|'Q'|'k'|'q', rooks?) -> square | -1`: the right's king stands on its first rank and `rooks[r]` (if given and holding that side's rook on that side of the king) else the outermost rook of that colour on that side of the king on that rank; -1 if none.
- Position field `pos.rooks: { K?, Q?, k?, q? }` (square indices), present only when some right's rook or king isn't standard (king e1/e8, rooks a/h). Copied unchanged by `applyMove` (the same object), so a 960 game stays 960 after rights are lost. Setups (`readFen().setup`, EditCore) carry `rooks` the same way.
- `ChessCore.is960(pos) -> boolean` = `!!pos.rooks`; `ChessCore.fenIs960(fen) -> boolean` via `readFen`.
- `ChessCore.castleMoves(pos) -> [{ side: 'a'|'h', step }]` the legal castles for the side to move in a 960 position (each `step` a `userMove`-shaped line step), `[]` for a standard one.
- `ChessCore.castleTarget(pos, from, to) -> 'a'|'h'|null` in a 960 position, whether a king drop on `to` (c or g of its first rank) is a legal castle.
- In a 960 position `legalMove(pos, kingSq, rookSq)` is the castle (king-takes-rook); `uci` of the castle is king square + rook square.
